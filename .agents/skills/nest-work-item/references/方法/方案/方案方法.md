# 方案方法

`方案/方案.md` 是工作项唯一当前 Technical Plan，负责把正式需求转换为可实施的技术决定。概要与详细仍是两种必要的抽象视角，但不再是强制阶段或两份固定文件：同一份活方案先说明目标结构、责任和取舍，再说明这些决定对组件、接口、流程和实施入口的具体影响。

方案只保留当前有效决定。研究、契约、时序和复杂实现细节按真实影响拆出，避免一份正文无限膨胀，也避免为了模板完整度制造文件。

## 产物与所有权

- `方案/方案.md`：必需。维护当前技术基线、责任边界、关键决定、实施路径、取舍、风险、材料导航、未决项和 Review 状态。
- `方案/研究.md`：条件产生。保存需要独立留档的研究结论与来源。
- `方案/契约/`：条件产生。保存需要独立留档的边界契约。
- `方案/时序图/*.puml`：条件产生。需要设计当前空间与直接上下游之间的跨边界交互时，按 [时序设计方法](时序设计方法.md) 一条链路一个 PlantUML 源文件。
- `方案/实现细节/*.md`：条件产生。保存需要从主方案拆出的实现细节。

持久化、领域、状态、配置和内部层间映射等内部模型决定随相关技术决定维护在 `方案/方案.md`；跨系统传输模型由 `方案/契约/` 维护。

不存在触发事实时不创建对应文件或目录。既有工作项的 `10-概要设计.md`、`20-详细设计.md`、`metadata/` 或其他历史布局不自动迁移；修改历史工作项时先识别当前活动基线，只有用户要求重构或旧布局已妨碍本次工作，才迁入上述结构并说明替代关系。

## 主方案内容

按实际复杂度回答：

1. 目标结果、范围、不做项、约束，以及当前机制与目标机制的差异。
2. 系统上下文、参与者、模块责任、数据所有权、信任边界和依赖方向。
3. 主要用户流程或系统主链路、关键输入输出、失败路径和最终可观察结果。
4. 核心技术决定、复用边界、替代方案、不选原因、代价、反例和改变条件。
5. 受影响模块、组件、文件或类型及其新增、修改、复用和退出关系，具体到执行能够拆成任务，但不逐行翻译源码。
6. 真实适用的状态、事务、并发、幂等、超时、取消、重试、补偿、资源释放、安全、性能、可观测性、兼容、迁移和回退边界。
7. 条件方案材料的触发结论和导航、验证观察点、待确认决定及其阻塞影响。

## 工作流

1. 回读工作项 README、正式需求、当前方案入口及本次决定涉及的源码、配置、契约和运行事实。
2. 先确认目标结构、责任归属和关键取舍，再展开其对组件、接口、流程和实施入口的影响；未知项写成明确阻塞，不用实现细节掩盖未决定的边界。
3. 命中条件产物时建立对应唯一事实源，主方案只保留结论和链接，不复制字段、协议或完整箭头链路。
4. 从主方案拆出小、可观察、可独立实施的任务；实施发现方案错误或事实变化时先更新事实所有者，再继续执行。
5. 验证后将实际实现、需求、方案、任务和证据收敛；偏差进入对应事实所有者，不在测试记录中悄悄改写设计。

## 完成判据

- 阅读者能从 `方案.md` 理解系统边界、责任、关键取舍和实施路径，不需要重新决定架构归属。
- 条件产物只在触发时存在，且每类事实只有一个所有者；主方案中的摘要与链接不形成第二正文。
- 当前事实、目标设计、未来候选和未知明确区分；方案不把计划写成已完成或测试通过。
- 实施前需求与事实仍有效，主方案与契约、时序和实现细节没有冲突，所需副作用授权已经成立。
- 文件齐全、图可渲染、构建成功或现有代码均不能单独证明方案正确。
