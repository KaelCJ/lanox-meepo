# 建档方法

本方法只用于已经存在的工作项，包括用户明确要求“创建并建档”且创建路径已经完整成功的新项。它在现有身份和目录内建立核心记录，不初始化索引、不分配编号、不创建另一个工作项。

核心记录为根 `README.md`、`需求/原始需求.md`、`需求/认知拉齐.md`、`需求/需求.md`、`方案/方案.md`、`执行/执行步骤.md` 和 `测试/测试验证.md`。`方案/研究.md`、`方案/契约/`、`方案/时序图/` 和 `方案/实现细节/` 全部按真实触发条件产生；没有触发事实时不创建文件、目录、模板或示例。

本方法只负责编排，不重复各文件规则。

## 顺序与输入

1. 原始需求：按 [原始需求方法](../方法/原始需求方法.md) 处理当前 Session 中与工作项相关的自然语言对话，记录用户原话、Agent 实际响应摘要及其关系，并清理明显过期且无独立恢复价值的记录。创建路径已写入的原话不得重复追加。
2. 认知拉齐：按 [认知拉齐方法](../方法/认知拉齐方法.md) 写入 `需求/认知拉齐.md`；已获用户确认或纠正的理解标为已确认，Agent 推断一律标为待确认。
3. 正式需求：按 [正式需求方法](../方法/正式需求方法.md) 写入 `需求/需求.md`；只采用已确认理解和核实事实，未确认项进入待确认清单，不冒充结论。
4. 方案：按 [方案方法](../方法/方案/方案方法.md) 写入唯一当前 `方案/方案.md`，在同一活方案中从目标结构、责任和取舍展开到可实施路径，不建立固定概要设计和详细设计文件。命中条件时创建对应专项材料；需要设计当前空间与直接上下游之间的跨边界交互时，按 [时序设计方法](../方法/方案/时序设计方法.md) 处理，主方案只保存决定和导航。
5. 执行步骤：按 [执行方法](../方法/执行方法.md) 写入 `执行/执行步骤.md`，将方案拆成小、可观察、可独立实施的任务；来源不足时记录真实阻塞，不建立空 DAG、步骤目录或伪状态。
6. 创建或覆盖 `测试/测试验证.md`，只保存当前测试结果；未执行时写“未执行”。
7. 按 [工作项 README 模板](../工作项README模板.md) 更新根 README：记忆摘要压缩形成当前形态所需的上下文；当前简介说明现在的定位和范围；当前停点写明建档实际完成项、仍待 Review 内容和下一步；工作项宪章只采用已确认或已核实的独有长期边界。
8. 更新索引 `updatedAt`，执行 `validate`，回读全部文件与记录。来源不足时如实记录待补充项，不逐层请求确认；只有继续需要不可逆操作、范围扩大或只有用户能补的信息时才停。

## Review 与持续核对

- 建档完成不等于需求已确认、方案已批准或实施已授权；全套记录整体进入用户 Review。
- Review 反馈先按原始需求方法记录用户原话和本轮 Agent 响应摘要，再更新认知拉齐（含被替代结论），然后按顺序传播到需求、主方案、受影响的条件方案、执行和当前测试记录；每层只改真实受影响内容。
- 后续 Session 先从根 README 的记忆摘要、当前简介、当前停点和工作项宪章恢复，再按动作加载对应方法；已完成的建档环节不重复执行。

## 边界

- 任何环节来源不足时如实写“待补充”，并写清需要用户提供什么；不创建空文件、占位模板或编造内容。
- 本方法不扩大实施、运行、提交、发布、跨仓或真实数据授权；建档产物是记录，不是验收。
- 结束前回读全部文件并校验两份权威索引，向用户报告建立或更新了哪些记录、当前状态、待确认清单和未验证边界。
