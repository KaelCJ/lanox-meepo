# 生成日报

## 识别输入

1. 同时支持单日、日期列表和连续范围，例如 `2026-07-20`、`0720,0723`、`0720-0724`。`MMDD` 缺少年份时，使用本次输入或当前对话最近一次明确年份；仍不唯一时只追问一次年份。声明月份或范围后，后续单独的 `20`、`21` 等数字按该范围内的日号解析；跨月且无法唯一定位时才追问。
2. 接受 `10-19`、`10-18.30`、`10:00-18:30` 等时间格式，将点号按时间分隔符解析。日期后的文字归为该日用户备注，直到下一日期开始。
3. 用户备注可为空；有备注时将其作为辅助证据和定向搜索关键词，不要求用户写成完整句子。
4. 默认每个工作日扣除午餐 1 小时；用户明确给出其他休息时长时以用户输入为准，不自行扣除晚餐。
5. 按“下班时间 - 上班时间 - 休息时间”逐日计算净工时，并四舍五入到最接近的 `0.5h`。结束时间不晚于开始时间时，除非用户明确说明跨日，否则标记输入冲突。
6. 单日缺少必要字段时只追问缺失字段。批量输入中个别日期缺少时间时，继续分析其他日期，也扫描该日工作内容但不分配工时；最终一次性列出缺失日期。不要把缺失日期擅自判为休息日，用户明确写明休息、请假时才跳过。

## 证据路线

按以下顺序取证：

```text
当天 Git → 工作项执行记录 → 当天 Session
```

这表示逐层补足事实，不表示前一层只要命中任意内容就立即停止：

- Git 证明当天已经提交的变更与交付对象。
- 工作项执行记录提供结构化目标、步骤、结果与当前状态；带有目标日实际动作和结果的执行记录可以独立证明该条工作项事实，不要求必须有 Git 或 Session，但无对应主题 Git 时仍必须扫描 Session，不能用一条工作项记录承接全天。`current.json`、`archive.json`、目录日期、文件 mtime 和仅有待办的 README 只用于导航，不能证明当天实施。README 或看板若本身作为执行记录明确写出目标日的实际动作与结果，可作为相应文档或治理结果证据；纯索引内容仍不算实施。
- Session 是当天真实活动账本。它可以独立证明当天发生过设计、实施、排查、验证或失败尝试；是否完成必须依据 Session 中的真实操作、结果和停止状态判断，不能只采信助手总结。
- 用户备注是直接输入，可补充其他仓库或线下工作，但不得伪装成 Git 提交、工作项记录或 Session 操作。

不查询或使用 `.workspace-assistant/90-演进/` 下的演进表、会话归档或其他派生演进材料生成日报。

## 第一层：当天 Git

从当前仓库根执行只读检查，不修改工作树、索引、工作项、Session 或历史：

开始取证时先冻结目标日期与本次日报输入完成时间；以最后一条用于确定日期、上下班时段、休息或备注的用户消息为上界，Git 结果也不得纳入该上界之后才出现的提交或工作树事件。

1. 用 `git rev-parse --show-toplevel` 确认仓库，并读取 `git config user.name`、`git config user.email`。
2. 单日一次取得当天提交；批量一次查询最早日期至最晚日期，再按本地日期分组。超过 7 天时按 7 天分块，避免逐日重复扫描：

   ```text
   git log --all --since="<first-date> 00:00:00 +0800" --until="<last-date> 23:59:59 +0800" --date=iso-strict --shortstat --summary --pretty=format:"%H%x09%an%x09%ae%x09%ad%x09%cd%x09%s"
   ```

3. 当前 Git 身份能唯一匹配时，只计入该身份的提交；多位作者且归属不明时，不把他人提交算入。
4. 某日 Git 结果为空时，用 author date 补查一次，避免只因 author/committer 日期差异漏记：

   ```text
   git log --all --pretty=format:"%H%x09%an%x09%ae%x09%aI%x09%cI%x09%s" | rg "<date-regex>"
   ```

5. 同时只读查看 `git status --short` 与必要的 `git diff --stat`，识别尚未提交的候选改动；工作树状态、文件 mtime 和未提交 diff 单独不能证明改动发生在目标日，必须由工作项执行记录或 Session 事件建立日期归属。

Git 输出中的 author/committer ISO 时间统一转换到 `Asia/Shanghai` 后分桶；不要把运行 Git 命令的机器时区或提交标题中的日期当成目标日。

仓库不是 Git、命令失败、浅克隆或权限导致 Git 不可用时，记录“Git 未能读取”及原因，仍继续工作项 → Session；Git 为空与 Git 不可用都不能中止后续取证。

提交标题和统计已经能形成具体工作结果时先保留候选；不要用变更行数直接换算工时。

## 第二层：工作项执行记录

在同一批中用一个日期正则定向搜索 `.workspace-assistant/10-工作项/`，同时覆盖进行中与已归档工作项：

- 优先从 `current.json` 与 `archive.json` 定位当前和已归档工作项，再在所有工作项目录（包括日期早于目标日的旧目录）内定向搜索带有目标日期的执行材料；日期匹配应覆盖 `YYYY-MM-DD`、`YYYY/MM/DD`、`MM-DD` 和常见中文日期写法。候选承载可包括 `README.md`、`执行/**`、`执行.md`、`执行步骤.md`、步骤总览、执行记录、进度、看板、测试/验证记录、产出说明或其他明确记录实际动作与结果的文件；不要把固定文件名清单当成穷尽规则。
- 候选发现和日期命中不设 4 项上限；深读时最多选择 4 个最相关工作项，每项读取 `README.md` 和最相关的一个执行总览或执行记录，必要时按入口补读最小证据。若候选超过 4 个，先按同一主题合并并用 Session 校正，不能静默丢弃候选。
- 仅创建目录、更新索引、日期命中、历史回顾或存在待办，不算当天已实施；但 README/看板/索引中明确记录目标日实际动作与结果时，可按文档或治理结果计入。
- 用记录日期、状态、结果和停止点过滤纯待办。复杂工作项可按其入口指向的最小记录补读，轻量工作项没有执行目录时不得因此判定无工作。
- 工作项正文没有当天日期时，不用文件修改时间推断当天工作；留给 Session 建立日期归属。日期行若只是历史回顾、计划、下一步或待办，也不能算当天实施。

Git 为空时，即使工作项已经命中并看似足够，也必须继续读取当天 Session；工作项可能未记、少记或晚记，不能用一个碰巧有日期的工作项承接全天工时。

## 第三层：当天 Session

逐日满足任一条件时触发 Session 取证：

- 没有与目标主题对应的有效当天 Git 证据，或提交无法可靠归属当前用户/主题；这是强制触发条件，不因工作项命中或存在其他无关提交而取消。
- 净工时不少于 `4h`，但 Git 与工作项合并后只能形成 0—1 个具体工作结果。
- 候选内容只有“更新、调整、优化、重构”等泛化动作，没有明确对象和结果。
- 一个尚不具体的主题将承接 `70%` 以上净工时。
- Git 与工作项互相印证不足，无法判断记录是实际实施、方案整理、排查尝试还是仅创建待办。
- 用户明确要求包含未提交工作、Session 或当天完整活动。

触发后，完整读取并执行 [Session 证据收集](references/session-evidence.md)。无 Git 时的顺序固定为：先扫描工作项执行记录以获得结构化线索，再读 Session 补齐和校正；不能在工作项命中后提前停止。

Session 若识别出此前未命中的工作项编号、路径或明确名称，再只读对应 `README.md` 和最相关的一个执行记录。工作项仍无记录时，直接保留 Session 已证明的真实主题，不虚构工作项归属。

## 定向深扫与停止条件

本 Skill 只做日报级近似归纳，不执行代码审计、构建、测试、浏览器操作、精确时间线重建或无边界搜索。首轮信息足够时停止；只有对应日期触发上述门槛时才深扫该日：

1. 对相关提交读取 `git show --format=fuller --stat --summary <hash>` 和 `git show --format= --name-status <hash>`，按 module 与交付对象识别真实子主题。
2. 仍不清楚时，只读取最多 5 个关键生产源码、配置或前端文件的最小 diff；不读取完整提交 diff，不扫描测试源码。
3. 对命中的工作项按上节范围读取执行记录；可回读相关现存产物确认结果仍存在，但现存文件或修改时间不能单独证明目标日期归属。
4. 需要确认工作项何时进入 Git 时，只查看该工作项路径的提交历史；后续 checkpoint 只能辅助解释目标日期记录，不能冒充目标日期提交。
5. Session 读取只覆盖目标日期、当前仓库和必要上下文，按 reference 的边界停止，不扩展为全历史会话分析。

深扫后仍只有一个真实主题时，保留一个主题并补充 2—3 个具体结果，不拆文件或 Session 凑项目。Session 显示只有排查、设计、失败尝试或未完成工作时，按真实状态描述，不能改写为“完成”。

证据冲突时保守处理：Git 只证明提交存在，工作项只证明其记录内容，Session 回执才证明对应操作结果；若工作项/README 写“完成”但目标日 Session 最终失败或阻塞，保留冲突并写排查/阻塞，不能选乐观结论。反之，Session 已证实的真实文档或治理动作可补足尚未更新的工作项记录。

始终只读原始证据，不修改或归档 Session，不读取任意聊天导出、导入资产、密码库或与目标日期无关的 JSONL 正文；仅可读取筛选所需的最小元数据或理解目标日事件所需的 preceding context，不扫描运行日志。凭据、Token、Cookie、Session 标识和其他敏感值不得进入日报、命令输出摘录或依据说明。

## 归并并分配工时

1. 逐日按真实工作主题合并 Git、工作项、Session 和用户备注；同一实现及其记录更新只算一项，父 Session 与子 Agent 的同一交付不重复计数。每天最多保留 4 项，证据不足时不凑数，不把工时跨日期调剂。
2. 排除当前“生成这份日报”的请求及其取证动作，但不要因此排除同一 Session 中其他独立、实质性的工作。
3. 每项只选一个固定权重：运行代码实现或重构 `4`，问题排查或验证 `3`，方案设计或工作项治理 `2`，归档、索引或纯文档同步 `1`。不要增加修正分，也不要用变更行数、Session 持续时间、消息数、Token 或工具调用数直接换算工时。
4. 以 `0.5h` 为最小分配单位，每项至少分配 `0.5h`。先按 `项目工时 = 净工时 × 项目权重 ÷ 权重总和` 计算，再按最大余数法分配 `0.5h` 单位，使每项均为 `0.5h` 的整数倍且总和严格等于净工时。
5. 当 `项目数 × 0.5h > 净工时` 时，先合并权重最低且语义相关的项目，直到满足每项至少 `0.5h`；不得输出低于 `0.5h` 的项目。
6. 描述以可汇报的工作结果为主，保留必要技术词，不堆叠文件名、提交号、Session 标识和工作项编号。

## 输出

默认逐日输出可直接复制的简短日报：

```text
<date> 日报（<start>–<end>，休息 <break>，有效工时 <net>）
- <工作结果>（<hours>）
- <工作结果>（<hours>）

合计：<net>
```

默认不展开分析过程。按实际使用的兜底证据追加一句简短依据说明：

- 无与该主题对应的当天提交但有工作项与 Session：`依据当天工作项执行记录与 Session 估算；未发现与该主题对应的当天 Git 提交。`
- Git 未能读取但有工作项与 Session：`依据当天工作项执行记录与 Session 估算；Git 未能读取。`
- 只有 Session：`依据当天 Session 的实际操作记录估算；未发现对应 Git 提交或工作项执行记录。`
- 只有工作项执行记录：`依据当天工作项执行记录估算；未发现与该主题对应的当天 Git 提交，Session 未提供额外有效证据。`
- 只有用户备注：`依据用户记录估算；Git、工作项执行记录与 Session 均无有效证据。`

Session 来源不可访问时，明确写“Session 未能读取”，不能写成“当天没有 Session”或据此判定没有工作；Git 命令失败时另写“Git 未能读取”，不要与“未发现提交”混淆。Git、工作项执行记录、可访问的 Session 和用户备注都没有有效证据时，请用户补充一个工作关键词，不编造日报。

批量输出按日期升序重复上述区块；默认不增加跨日总计。某日缺少时间时列出候选工作但不写工时，并在全部日报末尾一次性请求缺失时间。某日证据不足只影响该日，不阻塞其他日期。
