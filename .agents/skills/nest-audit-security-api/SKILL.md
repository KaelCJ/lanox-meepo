# API 代码安全审计

## 目标与边界

以每个实际可达的 API 为审计单元，依次建立完整 API 分母、逐 API 实际保护链和完整方法调用图，再把全部适用审计目标投射到真实执行路径，追踪到最终响应、数据访问或外部副作用。不得从单个注解、Filter、`if`、DTO 或类名直接得出安全结论。

默认只做只读源码与配置审计。除非用户明确要求，不修改代码、不启动服务、不发送请求、不创建测试资产。遵守目标仓库的入口规则与验证边界。

## 开始前

1. 确认用户指定的审计根目录或模块范围、组合根、部署入口和 Git 状态。未明确缩小范围时审计整个代码库，不自行抽样。
2. 使用目标当前宿主生效的项目治理入口，并只加载其为本次审计明确启用的规则或审计 Skill；不要因双宿主文件同时存在而重复读取。
3. 识别语言、Web/RPC 框架、安全框架、网关、ORM、缓存、消息、接口文档和代码生成机制。
4. 读取 [references/framework-signals.md](references/framework-signals.md) 中与当前技术栈有关的章节；只定位并加载相关章节。
5. G1 只依据框架信号、契约、装配和初步引用记录风险假设，不提前给 API 最终结论。每个 G2 深审 Agent 在开始逐目标判定前完整读取最新的 [审计目标](references/audit-targets.md)；同一有效上下文且文件未变化时复用，压缩、会话接续、文件变化或无法确认完整性时重读。需要风险定级或外部规则映射时再读取 [安全基线](references/security-baseline.md)。

## 执行协议：清单先行、逐 API 隔离、横向汇总

严格按 G1→G5 执行，不把全局初筛结果冒充 API 深审结论。第一阶段只建立分母和风险假设；第二阶段才对每个 API 独立还原真实执行链；第三阶段处理跨 API 流程与共享 sink；第四阶段做独立复核；第五阶段才汇总发布结论。

阶段门禁只证明动作和产物齐全，不证明 API 安全。每个 API 必须同时保存 `local_verdict`（接口自身逻辑）、`global_baseline`（继承的全局/部署问题）和 `release_verdict`（发布门禁），禁止因为 CORS、日志或构建配置等全局问题把所有 API 的局部逻辑统一标成同一严重漏洞。`未确认` 必须保留缺失证据、影响和阻塞的安全结论。

所有阶段共享唯一冻结分母、稳定 API ID、规则版本和状态账本。主 Agent 是分母唯一维护者；深审 Agent 只能处理分配给它的 API ID，不得新增、删除或重编号 API。API 较多时使用有界批次/队列，可并行但不可让 238 个任务无限制同时运行；没有子 Agent 能力时按相同 brief 顺序隔离地逐个执行。恢复或压缩后先读取账本，不能把未返回、部分返回或冲突结果当作完成。

产物目录、每 API 文件和 `verdict.json` 的固定 schema 见 [references/deep-audit-artifacts.md](references/deep-audit-artifacts.md)；如需机械创建或校验目录，优先使用 `scripts/init_api_audit.py` 和 `scripts/validate_api_audit.py`。

### G1：宏观枚举 API 分母与初筛清单

分别从以下来源枚举候选入口，再按组合根和部署事实交叉核对：

- HTTP/REST Controller、Router、函数式路由、GraphQL resolver、gRPC/RPC service、WebSocket/SSE handler、上传下载、Webhook、回调和管理端点；
- 应用挂载、组件扫描、条件装配、Servlet/Filter 注册、框架自动暴露、网关/反向代理路由和安全白名单；
- OpenAPI/Swagger、GraphQL schema、protobuf、前端/客户端调用点和部署配置。

为每个候选 API 记录稳定标识、协议和方法、完整路径或操作名、入口符号、所属模块、装配状态、暴露条件及证据位置。展开 path、query、header、cookie、body、multipart、消息负载和响应体，记录显式类型、嵌套字段和实际序列化结果。

结合路径、操作名、注释、出入参、调用方和产品语义描述 API 实际能力，并从契约直接产生后续必须验证的风险假设。例如，输入允许指定主体或资源而输出对应数据、凭据或高影响操作结果时，必须记录“调用者与目标对象的关系如何得到约束”，不能等扫描到某个权限判断后才提出问题。

单独记录代码、文档、网关、客户端和部署来源之间的差异。无法证明是否装配时标记 `未确认`，不能删除候选。

阶段产物必须落盘为一次审计运行目录（例如 `.api-security-audit/<run-id>/`）：`manifest.json`、`macro/api-inventory.csv`、`macro/protection-profiles.md`、`macro/global-findings.md`、`shared/domain-index.md`。每个 API 只在 manifest 中生成一个稳定目录名和初始 `agent/brief.md`，此时不得填写接口最终漏洞结论。

阶段门禁 G1：所有来源均已枚举和交叉核对；每个候选 API 都有稳定标识、入口证据、装配状态、出入参和意图/风险假设；差异与未确认项均已入表。

### G2：每个 API 独立深度审计

G1 冻结后，为 manifest 中的每个 API 建立独立深审任务。每个任务只接收：该 API 的 manifest 记录、G1 宏观组件/域模型索引、相关源码路径和本 Skill/相关 references；不得预先读取其他 API 的 findings 或 verdict，以免全局初筛和相邻接口结论污染当前 API。共享模型可以引用，但必须记录当前 API 实际使用的字段、关系和分支。

有子 Agent 能力时，一个 API 对应一个独立深审 Agent；主 Agent 只负责调度、回收、schema 校验和状态账本，不替子 Agent 把摘要拼成“已审计”。没有子 Agent 时，主 Agent 必须为每个 API 重置工作上下文，按同一 brief 顺序完成，不能把多个 API 压成一段统一结论。

每个 API Agent 必须独立产出：

1. `contract.md`：完整路径、方法、装配、输入/输出、实际序列化、接口意图和风险假设；
2. `protection-chain.md`：命中的网关、白名单、Filter、Guard、参数校验、异常和响应链，含匹配顺序与失败行为；
3. `call-graph.md`：Controller/Handler → 实际 Service/实现 → Repository/Mapper/缓存/文件/消息/外部系统 → 响应或副作用，含行号、分支、缓存、异步、重试、fallback 和上下文传递；
4. `sequence.mmd`：至少表示外部调用者、网关/保护组件、Handler、关键 Service、数据源/外部系统和最终响应/副作用的时序；无下游时画出有界的未确认节点；
5. `data-model.md` 与 `data-model.mmd`：本 API 实际触及的主体、目标对象、owner/tenant 关系、敏感字段、状态字段和 source/sink，不要只复制全仓库实体定义；
6. `findings.md`：每条发现包含严重度、优先级、入口/参数、证据链、影响、成立前提、修复方向和置信度；
7. `unconfirmed.md`：缺失的部署、运行时、外部实现或业务归属证据及其阻塞的判断；
8. `verdict.json`：按固定 schema 分离局部逻辑、全局基线和发布门禁结论。

当前 API Agent 先从安全配置、组件注册、网关、框架扩展点、注解和异常/响应配置核对候选保护组件，再只映射当前 API，按真实执行顺序追踪入口前后所有实际命中的横切控制：

`外部入口 → 网关/代理 → Security Chain → Filter/Middleware → Interceptor/Guard → Aspect/Decorator/方法安全 → 参数绑定与校验 → Handler → 异常处理 → 响应包装/脱敏/序列化`

对每个组件记录：

- 注册、挂载或装配证据；
- 匹配规则、顺序、方法范围、启用条件、排除路径和白名单；
- 提取、验证或信任的身份及安全上下文，以及如何传给后续调用；
- 允许、拒绝、异常和降级行为是否终止当前请求；
- Aspect 的 pointcut、注解解析、代理对象、自调用和未被代理入口；
- 多条安全链、路由组或异常处理链中当前 API 实际命中的一条。

存在全局 Filter、登录注解或权限框架只说明候选控制存在，不证明当前 API 受保护。无法闭环时在该 API 行标记 `未确认`，保留已确认部分和缺失环节。

此阶段的组件证据必须写入当前 API 的 `protection-chain.md`；G1 的 `macro/protection-profiles.md` 只用于索引和交叉核对，不能代替当前 API 证据。全局问题写入 `macro/global-findings.md`，在 API 的 `verdict.json` 只记录是否实际影响该 API，不复制成接口自身漏洞。

在 `audit-targets.md` 完整读取后，对当前 API 的每个适用目标建立端到端证据链：

`资产/主体/目标对象 → 不可信输入或触发条件 → source → 安全不变量 → 当前 API 的实际控制及覆盖路径 → sink/最终响应/副作用 → 可利用结果`

控制只有同时满足以下条件才可记 `通过`：命中当前 API 和当前分支、使用可信主体和正确对象、位于 source 到 sink 的有效位置、失败默认拒绝并终止、覆盖异常/缓存/异步/fallback、且后续查询和响应映射没有丢失约束。认证凭据、Session、Token、Cookie、API Key、密钥和重置材料一旦出现在当前 API 的响应、下载、日志或可调用副作用中，必须建立独立 finding。

G2 门禁：manifest 中每个 API 都有一份独立 brief 和深审目录；每份目录的必需文件齐全；保护链、调用图、数据模型、时序图和逐目标证据均有定位或明确未确认；`verdict.json` 可解析且没有把全局基线冒充局部结论。未完成、冲突或阻塞的 API 必须标记 `blocked/needs_review`，不能统计为通过。

### G3：跨 API 业务流程、共享能力和变体分析

G2 全部回收后才进行横向分析，避免在独立深审阶段提前用另一个 API 的结论替代当前 API 证据。按业务域和共享 sink 建立 `shared/flows/<flow-id>/`、`shared/variants/<variant-id>/`，至少覆盖：

- 登录/刷新/登出/重置/二次验证等认证生命周期；
- 提交→审核→记账→支付/充值等高影响状态机；
- 上传→绑定→下载/预览→删除等文件生命周期；
- 同一 Mapper/Service/Redis key/外部 Client 的所有消费者；
- 批量、列表、导出、父子对象、缓存、异步、重试、fallback 和内部/管理旁路。

跨 API Agent 可以读取 G2 的结果，但必须给出参与的 API ID、跨接口状态/数据流、共享 sink、缺失控制、可利用组合和影响范围；发现新 API 时退回 G1，发现新的分支时补回对应 API 的 G2，不得仅在汇总报告中追加未建模对象。

G3 门禁：所有已识别的跨 API 流程和共享能力均有参与 API ID、证据位置和影响记录；新增对象已回填 manifest 和对应 API 目录；横向结论没有覆盖或篡改单 API 的原始证据。

### G4：独立复核与冲突处理

对所有 P0/P1、认证/会话、Token/凭据、支付/充值、管理/审核、文件/OSS、拟判 `通过` 的 API 至少执行一次独立复核。复核 Agent 从源码和证据位置重新判断，不以主审摘要为事实；随后再对照主审结果。冲突时保留两个判断和证据，API 状态设为 `needs_review`，不能自动选择更乐观结论。

G4 门禁：指定 API 均有 reviewer 结果；所有冲突、证据失效和新增未确认事实都回填 API 目录与账本；没有把“主审没有发现”当成复核通过。

### G5：结论、优先级和人工排除

每个维度只使用：

- `通过`：有端到端证据证明控制覆盖全部相关执行路径；
- `失败`：有证据证明缺失、可绕过、暴露或契约本身形成不安全能力；
- `未确认`：关键装配、匹配、调用分派、业务归属或运行条件证据不足；
- `不适用`：有执行图和语义证据证明当前目标客观不存在。

同一目标已存在明确失败但仍有其他未知分支时，主状态记为 `失败`，同时把未知分支保留在未确认事实清单；不得因为已有失败就停止追踪或从未确认统计中删除。阶段状态、目标主状态和未确认事实是三个不同口径，不能互相代替。

业务可能合理、接口可能只供内部使用、调用者可能是管理员或风险可能暂时接受，都不能由审计者自行转换为 `通过` 或 `不适用`。先报告发现或未确认项；只有用户在看到具体 API、路径、影响和缺失控制后明确决定，才能另记为 `用户确认排除/风险接受`。该记录不改变原始技术状态，也不能作为安全证明。

总体结论仍遵循失败关闭，但只对 `release_verdict` 汇总：存在任一局部失败、适用的全局基线失败、跨 API 失败或未解决的 P0/P1 冲突时总体不通过；不存在失败但存在未确认时不得宣称安全通过。接口自身 `local_verdict`、继承的 `global_baseline` 和发布 `release_verdict` 必须分别统计。用户确认排除项必须在总体结论旁单独披露，且不改变原始技术状态。

## 输出要求

第一行直接给出总体判断，再报告高风险发现和覆盖情况。每条发现包含：严重度、受影响 API、入口与出入参、保护链、方法调用图、source/sink 或副作用、可造成的影响、成立前提、证据文件与行号、修复方向和置信度。把事实、推断和用户决定分开。

问题证据不得复述凭据、Token、Cookie、Authorization、Session 标识、密钥或其他敏感值；只保留定位和判断所需的脱敏信息。

至少输出以下关联产物；接口较多时保存为 Markdown/CSV 并在回复中摘要：

1. G1 宏观清单：API 暴露面与契约、候选保护组件、域/共享能力索引和全局基线问题；
2. 每 API 独立目录：契约、保护链、调用图、source/sink、`sequence.mmd`、数据模型、逐目标证据、发现、未确认事实、review 和 `verdict.json`；
3. G3 跨 API 产物：业务流程、共享 sink、变体和横向影响记录；
4. G4 独立复核记录；
5. G5 汇总矩阵和报告，必须同时展示 `local_verdict`、`global_baseline`、`release_verdict`、严重度、优先级、置信度和发现 ID；
6. 失败、未确认、匿名、模糊契约、敏感凭据和用户确认排除清单。

主矩阵至少包含：

| API | 入口/装配 | 意图与出入参 | 实际保护链 | 方法调用图 | 数据源/副作用 | 审计目标状态 | 局部结论 | 全局基线 | 发布结论 | 严重度/优先级 | 发现 ID |
|---|---|---|---|---|---|---|---|---|---|---|---|

报告覆盖统计必须以 G1 的统一分母为准，给出 API 总数、G1 清单完成数、G2 独立深审完成/阻塞数、G3 流程与变体完成数、G4 复核完成数、证据闭环数量、含未确认数量，各审计目标 `通过/失败/未确认/不适用` 数量，以及 `local_verdict`、`global_baseline`、`release_verdict`、严重度、优先级和未确认事实总数。不要用全局基线失败、阶段门禁通过、发现数量或目标已经失败来掩盖某个 API 尚未独立深审的事实。

## 完成标准

只有同时满足以下条件才称为完成：

1. G1-G5 全部满足，且各阶段产物使用同一 API 分母；
2. 每个实际装配 API 都有出入参和意图、实际保护链、完整方法调用图及逐目标状态；
3. 每个 API 已追踪到全部已知最终响应、数据访问和外部副作用，而不止 Controller 或第一层 Service；
4. 所有通过项都有端到端证据，所有失败和未确认项都有可定位路径；
5. 所有高风险契约信号均形成独立审计项，没有因通用控制或业务猜测静默跳过；
6. 报告明确区分源码静态事实、运行时未确认事实、技术状态和用户排除决定；
7. 没有执行用户未授权的请求、测试、修改、风险接受或范围缩减；
8. G2 中每个 API 都有独立 Agent/brief、独立目录和完整深审产物，不能以一张批量矩阵、共享摘要或全局扫描替代；
9. 汇总同时保留 `local_verdict`、`global_baseline`、`release_verdict` 和跨 API 结论，优先级以可利用影响和证据置信度排序，而不是按失败行数排序。
