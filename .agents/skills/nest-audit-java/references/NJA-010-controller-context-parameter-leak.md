# NJA-010 Controller 污染业务入参

## 元数据

- 状态：Ready
- 类型：Code Smell
- 质量属性：可维护性、安全性
- 默认级别：重大
- 标签：spring-mvc、controller、dto、context
- 适用范围：客户端可提交服务器拥有的身份、租户、权限或链路上下文字段；Controller 到 Service 的参数形态仅在目标项目明确启用相应 Java Rule 时检查

## 为什么是问题

把服务器拥有的用户、账号、租户、权限、trace 或语言上下文写入客户端可提交的请求 DTO，可能造成身份伪造、污染业务契约和多套上下文真源。Controller 把这些信息作为额外参数传给 Service 是否违规，取决于目标项目是否已定义统一上下文能力和 Controller—Service 签名规则；显式、受控且由架构拥有的上下文对象不能仅因是第二参数被判为问题。

## 触发调查

- 目标项目已要求只传完整请求 DTO 或无参调用，但 Service 方法仍同时接收 userId、tenantId、traceId 等额外参数；
- 目标项目已要求传递完整请求 DTO，但 Controller 仍把它拆成多个业务参数；
- 在已有统一上下文能力之外，为透传同一信息新增包装 DTO、Context 参数或手工读取工具；
- 客户端请求体可以提交服务器应掌握的身份、权限或 trace 字段。

## 判定所需证据

1. 确认参数来自客户端业务输入还是服务器上下文；
2. 定位项目统一身份、租户、权限和 trace 上下文能力；
3. 追踪 Service 的其他非 HTTP 消费者及异步跨线程需求；
4. 核对请求 DTO 的外部契约和信任边界；
5. 判断当前链路是否确有上下文快照、代操作或后台任务硬边界。

## 不应报告

- 参数是当前业务请求 DTO 中真实、可由客户端提交的业务输入；
- 无业务输入时 Service 使用无参方法；
- 异步跨线程、后台任务、管理员代操作或非 HTTP 调用确需显式且受控的上下文快照；
- 项目统一边界明确要求特定上下文对象，且不会污染客户端 DTO。
- 目标项目没有启用“完整 DTO 或无参”限制，显式上下文由单一架构边界创建、校验和消费，且不存在客户端伪造或多真源。

## 示例

不合规：客户端可在 `req` 中提交服务器拥有的 userId 或 tenantId，后端没有重新建立可信上下文。

目标项目启用完整 DTO 与统一上下文规则时，不合规：`service.execute(req, currentUserId, traceId)`；合规：Controller 只传完整业务请求 DTO，Service 从项目统一能力取得服务器上下文。特殊跨线程边界仍可使用经确认的显式快照设计。

## 最小修复

删除客户端可控的服务器上下文字段，改从可信边界建立上下文。目标项目已启用完整 DTO、无参调用或统一上下文规则时，再删除违反该规则的额外参数并接入真实所有者；未启用时按当前架构修复多真源或伪造风险，不强制改成单一 DTO。基础设施能力缺失时停止在 Controller 或 Service 临时补偿，转入获准的基础设施所有权范围。

## 报告要求

列出参数来源、客户端可控性、目标项目启用的规则与统一上下文入口、非 HTTP 消费者、特殊边界反例和最小签名调整；没有项目规则证据时不得仅按参数数量判定命中。
