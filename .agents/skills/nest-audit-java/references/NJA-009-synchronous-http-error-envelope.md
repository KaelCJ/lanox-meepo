# NJA-009 同步 HTTP 异常被包装为普通响应

## 元数据

- 状态：Ready
- 类型：Bug
- 质量属性：可靠性、安全性
- 默认级别：重大
- 标签：spring-mvc、exception、advice、trace
- 适用范围：Spring MVC 同步调用链向客户端泄露底层异常细节，或错误信封、状态码和日志行为违反目标 API 已确认契约；“异常必须交统一 Advice”只在目标项目明确启用该规则时检查

## 为什么是问题

同步请求失败后返回普通失败 DTO 并不天然错误；有些 API 明确采用 HTTP 200 加业务错误信封。真正通用的风险是响应泄露底层路径、命令、协议、堆栈或敏感 cause message，或当前实现违反目标 API 已确认的错误契约。目标项目明确要求统一 Advice 时，局部 catch、失败 DTO 和重复日志还会形成第二套错误处理真源。

## 触发调查

- Controller 或 Service catch 后返回 `failureResponse`、错误 `Map`、状态 DTO 或局部错误码，且可能违反已确认契约；
- 普通响应 DTO 含仅用于 HTTP 失败的 `code/message/error/traceId`，但没有可定位的错误信封契约；
- catch 中把底层异常消息、堆栈、路径或协议内容写进响应；
- 目标项目已明确统一日志所有者，但同一异常仍在业务层和 Advice 重复记录。

## 判定所需证据

1. 确认链路是尚未提交响应的同步 HTTP 请求；
2. 定位目标 API 已确认的状态码、错误信封、敏感信息和日志契约；目标项目要求统一 Advice 时再核对其入口；
3. 追踪 catch 后实际 HTTP 状态、响应体、日志和 cause 是否保留；
4. 区分真实领域状态与 HTTP 传输失败；
5. 检查资源回收、重试、降级、批处理或协议适配是否构成保留 catch 的必要边界。

## 不应报告

- catch 只负责资源回收或 checked exception 适配，并继续以 cause 抛出；
- 异步任务、批处理隔离、重试降级、响应已提交的 SSE/流式边界；
- DTO 字段表达真实业务或生命周期状态，不是 HTTP 异常信封；
- 项目没有统一 Advice，但错误信封是已确认契约且已净化敏感信息；本规则不能据此强制引入 Advice。
- HTTP 200 加业务错误信封是当前 API 的稳定契约，消费者、状态码和日志行为一致，且没有泄露底层细节。

## 示例

不合规：Controller 捕获所有异常，把 `ex.getMessage()` 中的文件路径或远端协议正文返回给客户端；或当前 API 明确要求非 2xx 与统一 Advice，却返回 HTTP 200 的局部错误信封。

合规：API 已明确采用经过净化的业务错误信封，Controller 保持该状态码和结构且不泄露底层细节。目标项目启用统一 Advice 时，预期业务失败使用稳定异常，非预期失败保留 cause 交给 Advice。

## 最小修复

先移除底层异常详情并恢复目标 API 已确认的状态码、错误结构和日志所有权。只有目标项目明确启用统一 Advice 规则时，才删除与其竞争的失败 DTO 包装和重复日志，让异常传播到该入口；保留必要 catch 时只处理当前边界职责。

## 报告要求

给出 catch 位置、目标 API 的已确认错误契约、当前 HTTP 行为、泄露或丢失的异常信息、日志所有者和适用例外。要求交给 Advice 时必须给出目标项目启用该规则及 Advice 可达的证据；缺少契约证据时不因失败 DTO 或 HTTP 200 单独判定命中。
