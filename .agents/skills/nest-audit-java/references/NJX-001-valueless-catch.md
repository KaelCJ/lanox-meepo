# NJX-001 无处理价值的 catch

## 元数据

- 状态：Ready
- 类型：Code Smell
- 质量属性：可维护性、可靠性
- 默认级别：普通
- 标签：exception、catch、rethrow、wrapping
- 适用范围：Java 中新增或保留的异常捕获、包装、记录和重抛

## 为什么是问题

没有恢复、清理、状态收敛或协议责任的 `catch` 只增加控制流和异常壳，使调用方误判当前层拥有错误处理职责。沿调用链重复出现时，还会掩盖原异常并扩大排障成本。

## 触发调查

- `catch` 只有 `throw error`、新建异常、修改 code/message、日志后重抛，或这些动作的组合；
- 同一异常沿多层被补充相似文案、错误码或通用类型；
- 私有或内部方法只为隐藏受检异常声明而增加包装。

## 判定所需证据

1. 定位原异常来源、完整 `catch` 动作、全部生产调用方和最终入口；
2. 核对当前层是否执行恢复、补偿、资源清理、中断恢复、重试、失败状态收敛或真实协议转换；
3. 核对消费者是否稳定依赖包装后的类型、错误码、字段或状态；
4. 对照删除整个 `try-catch` 后的异常实例、类型、cause、堆栈、状态和失败时序。

## 不应报告

- 当前层执行了有契约依据且上层无法等价完成的真实处理；
- 框架或外部接口要求把受检异常适配为既有非受检协议；
- `catch` 恢复中断标记、释放资源、添加 suppressed、回滚、补偿或隔离单条批处理失败；
- 尚未核实调用方、入口和处理责任。

## 示例

不合规：内部写入方法捕获 `IOException`，只抛出带相似文案的新运行时异常，且没有消费者依赖该类型。

合规：任务入口捕获异常后更新有契约依据的最终失败状态，再原样传播，因为上层无法等价完成该状态收敛。

## 最小修复

删除无处理价值的整个 `try-catch`，按目标项目允许的方式保留原异常实例、类型、cause 和堆栈传播；同步删除只服务该包装的声明或文档，不改造相邻异常体系。

## 报告要求

给出原异常来源、`catch` 动作、调用方、最终入口、已排除的真实处理责任、删除后的行为差异和最小修复。
