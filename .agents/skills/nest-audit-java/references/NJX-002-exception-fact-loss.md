# NJX-002 异常事实被改写或因果链丢失

## 元数据

- 状态：Ready
- 类型：Bug
- 质量属性：可靠性
- 默认级别：重大
- 标签：exception、cause、stacktrace、interrupt、error
- 适用范围：异常包装、类型转换、消息提取和宽泛异常捕获

## 为什么是问题

包装如果丢失原类型、cause、堆栈、中断或致命错误语义，调用方和入口就无法按真实故障分流，日志也无法还原根因。保留相似 message 不能替代异常事实。

## 触发调查

- 新异常没有保留 cause，或只复制 `getMessage()`；
- 把 `Exception`、`Throwable`、`Error` 或中断异常转换为普通业务异常；
- 从 message 反推异常类别，或沿多层重复改写类型、文案和错误码。

## 判定所需证据

1. 对照转换前后的运行时类型、cause、堆栈、中断标记、致命错误和结构化字段；
2. 定位按异常类型、错误码或字段分流的真实消费者；
3. 核对当前层是否真正拥有必须转换的外部协议；
4. 证明事实丢失会造成错误归类、错误恢复、错误日志或不可诊断结果。

## 不应报告

- 真正拥有协议的边界按既有契约转换异常，并完整保留 cause、必要字段和致命错误语义；
- 安全边界只替换用户可见文案，内部仍保留完整异常供日志和诊断；
- 只有包装形状，尚不能证明任何异常事实或消费者分流受损。

## 示例

不合规：捕获 `InterruptedException` 后抛出没有 cause 的普通业务异常，既未恢复中断标记，也使任务入口无法识别取消。

合规：RPC 边界按既有错误协议生成状态对象，同时保留原 cause 供边界日志记录，并正确处理不可恢复错误和中断。

## 最小修复

优先传播原异常；确有转换契约时保留完整 cause、中断和致命错误语义，以及消费者需要的结构化事实，不从 message 推断类别。

## 报告要求

列出转换前后丢失或改写的事实、受影响消费者和入口、具体错误行为、协议反例核对及最小保真修复。
