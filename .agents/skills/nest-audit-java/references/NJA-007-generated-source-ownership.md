# NJA-007 破坏生成代码所有权

## 元数据

- 状态：Ready
- 类型：Code Smell
- 质量属性：可维护性、可靠性
- 默认级别：重大
- 标签：generated-code、ownership、schema、codegen
- 适用范围：生成器拥有的 Java 源码、schema、模板、生成配置和人工扩展层

## 为什么是问题

直接修改生成产物会在下次生成时丢失，或形成生成真源与人工补丁两个事实来源。为了格式、注释、Lombok 或扫描结果手改产物，通常无法稳定维护，还可能破坏框架兼容。

## 触发调查

- 文件头、目录、构建插件或注解表明源码由生成器拥有；
- 同一结构同时存在 schema/模板和手工字段或方法；
- 生成命令再次运行会覆盖当前改动；
- 为满足风格或静态规则批量修改生成目录。

## 判定所需证据

1. 定位生成器、schema、模板、配置和输出目录；
2. 确认目标文件是否允许受保护的人工扩展区；
3. 检查当前任务是否授权修改生成真源和重新生成；
4. 证明人工改动会被覆盖、与真源不一致或破坏生成契约。

## 不应报告

- 文件是人工维护代码，只是名称或注解看起来像生成产物；
- 生成器明确提供并保留人工扩展区，改动仅位于该边界；
- 当前需求已授权修改 schema/模板并重新生成，产物与真源一致；
- 只读审计对生成产物描述事实，没有要求其机械满足人工代码风格。

## 示例

不合规：在生成 DTO 中手加字段和 getter，却保留未修改的 schema；下一次生成会丢失字段。

合规：修改获准的 schema 或模板，重新生成并验证消费者；真源不在授权范围时停止结构性修改并报告。

## 最小修复

撤回人工产物改动，在授权范围内修改生成真源并重新生成；无法修改真源时使用生成器正式支持的扩展机制，或停止受影响实现，不建立平行模型副本。

## 报告要求

指出生成所有者、真源、覆盖机制、当前人工差异、重新生成风险和可用的正式扩展边界。
