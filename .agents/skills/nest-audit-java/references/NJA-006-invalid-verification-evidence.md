# NJA-006 验证证据与结论不匹配

## 元数据

- 状态：Ready
- 类型：Code Smell
- 质量属性：可靠性、可维护性
- 默认级别：重大
- 标签：testing、evidence、verification、regression
- 适用范围：使用编译、静态检查、局部测试、Mock、旧 proof 或旁路调用证明当前行为的改动

## 为什么是问题

证据没有经过受影响的真实入口、身份、数据和状态时，绿色结果只能证明局部对象，不能证明用户行为。把局部检查写成测试通过会掩盖真实回归，使后续决策建立在无效基线上。

## 触发调查

- 只运行 compile、package、源码扫描或结构断言就宣称功能通过；
- Mock/Fake、Controller 直调或 API-only 检查替代真实用户入口；
- 沿用改动前、旧制品、另一分支或另一环境的 proof；
- 只覆盖全新数据，没有覆盖受影响的历史会话、缓存、角色或持久状态。

## 判定所需证据

1. 明确结论声称证明的需求、入口和行为；
2. 核对被测制品、版本、环境、身份、数据和前置状态；
3. 追踪实际动作是否经过受影响代码与最终用户可见结果；
4. 对照项目对“自动检查”“真实测试”和“验收”的当前定义；
5. 指出证据缺失导致不能推出的具体结论。

## 不应报告

- 结论准确限定为“编译成功”“自动检查通过”或“未执行真实测试”；
- 当前验收对象本来就是文件结构、格式或确定性静态规则；
- proof 与当前制品、入口、身份和状态完全匹配且覆盖受影响路径；
- 用户只要求局部检查，结果没有被扩大解释。

## 示例

不合规：Controller 修改后只直接调用 Service 并断言 DTO，随后记录“用户流程测试通过”，没有真实鉴权、HTTP、页面和历史状态。

合规：把局部结果称为自动检查，并明确真实入口未执行、缺少哪些前置以及当前不能证明什么。

## 最小修复

收窄结论到证据实际覆盖范围；需要产品行为结论时，按项目口径运行当前制品的真实入口并记录新证据。旧失败和未执行事实不得无痕覆盖。

## 报告要求

列出原结论、实际证据类型、被测对象身份、缺失入口或状态，以及允许保留的最窄结论。
