# NJA-003 无当前依据的扩展点

## 元数据

- 状态：Ready
- 类型：Code Smell
- 质量属性：可维护性
- 默认级别：普通
- 标签：design、speculative-generality、interface、factory
- 适用范围：Interface、Factory、Strategy、Provider、Plugin、Registry、配置开关和可替换实现

## 为什么是问题

没有当前消费者、替换需求或多个实现的扩展点把未来猜测写进现有架构。它会扩大公共契约、组合数量和兼容责任，并使简单行为必须穿过多层选择机制。

## 触发调查

- 接口只有一个实现且没有运行时或构建时替换；
- Factory、Registry 或配置开关只有一个分支；
- JavaDoc 主要解释“未来可以扩展”，不能说明当前用途；
- 为测试方便新增接口，但生产代码没有真实边界需要隔离。

## 判定所需证据

1. 搜索全部实现、消费者、SPI、反射、配置和依赖注入注册；
2. 核对当前需求、正式方案和外部契约是否要求替换能力；
3. 构造直接依赖唯一实现的最小方案，并比较兼容与认知成本；
4. 证明移除扩展点不会破坏真实边界或多个生产消费者。

## 不应报告

- 框架或外部 API 明确要求接口、Provider 或 SPI；
- 当前已有多个真实实现，或部署时确实选择不同实现；
- 接口隔离不可控外部系统、安全、事务或生命周期边界；
- 公共库对已发布消费者负有兼容责任，且当前范围不能收回契约。

## 示例

不合规：为唯一算法创建 Interface、默认实现、Factory 和配置项，当前部署永远选择默认实现，需求也没有替换场景。

合规：同一契约有两个生产实现，由当前租户或运行环境选择，并且调用方不依赖实现细节。

## 最小修复

删除未使用的选择层，让当前所有者直接依赖最小实现；保留未来演进空间只能作为说明，不能预建代码。若接口由外部契约强制，删除多余 Factory 或配置分支而保留必要边界。

## 报告要求

列出实现和消费者、当前选择机制、需求依据、直接实现反例以及已检查的框架或兼容约束。
