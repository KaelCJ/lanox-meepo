# NJA-002 无价值间接层

## 元数据

- 状态：Ready
- 类型：Code Smell
- 质量属性：可维护性
- 默认级别：普通
- 标签：design、indirection、processor、helper
- 适用范围：新增或扩大的 Processor、Helper、Service、Adapter、Facade、包装层及相似中间类型

## 为什么是问题

只转发参数或搬运线性流程的中间层不会隐藏复杂度，却增加文件跳转、构造依赖、命名和测试表面积。调用者仍需理解全部细节时，抽象没有形成稳定边界，修改成本反而上升。

## 触发调查

- 只有一个生产调用方、一个实现和一个 `process/execute/handle` 方法；
- 方法无独立状态，只把调用者已有参数原样传给下游；
- 新类型没有减少调用者的分支、状态或领域知识；
- 测试只直接调用新类型，未覆盖真实入口。

## 判定所需证据

1. 搜索全部生产消费者、实现、注册和构造路径；
2. 构造把逻辑放回唯一调用方的最小内联版本；
3. 比较内联前后的参数数量、跳转、重复、职责泄漏和边界损失；
4. 证明当前类型没有独立算法、外部 IO、事务、安全、并发、生命周期或框架适配责任。

只有单一调用方或方法短不能单独判定命中。

## 不应报告

- 类型隔离外部系统、事务、资源生命周期、安全或框架回调；
- 存在多个共享同一语义的真实生产消费者；
- 承载可独立命名且有实质复杂度的算法、状态机或业务规则；
- 现有稳定架构要求该边界，内联会造成循环依赖或真实重复。

## 示例

不合规：Controller 把已有的请求 DTO、用户 ID 和配置继续传给唯一 `RequestProcessor`，Processor 只顺序调用两个 Service，未隐藏新语义。

合规：独立组件拥有重试、关闭、超时和资源释放生命周期，调用者只依赖稳定输入输出，不需要知道内部步骤。

## 最小修复

在保持行为等价的前提下删除中间层并内联到真实所有者；不要顺带重命名、拆包或扩展其他调用链。若确有硬边界，收窄接口到能隐藏该边界的最小契约。

## 报告要求

给出生产调用方数量、实际方法行为、反事实内联结果、已排除的硬边界和预计减少的认知跳转。
