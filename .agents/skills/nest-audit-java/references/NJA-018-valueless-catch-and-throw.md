# NJA-018 无处理价值的 catch-and-throw

> 本规则已废止。异常捕获与传播由 `$nest-audit-java` 的异常专项模式及 `NJX-*` 规则负责；本文件只保留原编号和迁移记录，不再用于新增审计结论。

## 元数据

- 状态：Deprecated
- 替代：`$nest-audit-java` 异常专项模式的 `NJX-001`—`NJX-005`
- 类型：Code Smell
- 质量属性：可维护性、可靠性
- 默认级别：普通
- 标签：exception、catch、rethrow、wrapping、SneakyThrows、error-contract
- 适用范围：Java 中新增或保留的异常捕获、包装、重抛和受检异常收口；不把所有 catch 或异常转换机械判为问题

## 为什么是问题

catch 如果既不恢复、不清理、不形成消费者依赖的稳定异常协议，也不承担必要观测或框架适配，只把原异常原样抛出或套进另一个异常，会增加控制流跳转并掩盖真实失败类型。多层重复包装还会让 Advice、调用方、日志与排障代码面对无意义的异常壳，误以为每一层都拥有错误处理责任；宽泛捕获 `Throwable` 后换成普通异常时，甚至会破坏 `Error`、中断和最终状态语义。

## 触发调查

- catch body 只有 `throw e`、`throw new RuntimeException(e)`、`throw new IllegalStateException(message, e)`、`throw new DwException(e)` 或同义换壳；
- 先捕获 `RuntimeException | Error` 原样抛出，再捕获剩余 `Throwable` 统一包装；
- 私有或内部方法只为隐藏 `IOException`、`Exception`、`Throwable` 的编译声明而新增 catch；
- 同一异常沿调用链被多次补充相似文案、错误码或通用异常类型，但没有消费者按每层协议处理；
- 删除包装后观测变量、finally 状态或异步完成状态可能不再覆盖原始受检异常。

## 判定所需证据

1. 定位 catch 所在方法的接口/父类约束、全部生产调用方、统一 Advice、异步或框架入口；
2. 核对目标异常类型、错误码和消息是否被当前消费者用于恢复、协议映射、响应、重试、回退或批处理隔离；
3. 核对 catch 是否承担资源/状态清理、事务、锁、线程中断恢复、SSE/回调适配、用户明确要求的最终状态或框架规定的责任；
4. 对照最小直接传播方案，确认删除 catch 后原异常实例、运行时类型、堆栈、cause、清理、观测和失败时序如何变化；
5. 若底层声明受检异常，按目标项目规则核对最小非协议方法可用的收口方式；`@SneakyThrows` 的具体形态不决定 catch 是否有处理价值；
6. 单独核对 `InterruptedException`、`Error` 和资源所有权，不能把普通换壳精简扩张为吞中断、漏清理或错误降级。

## 不应报告

- 当前消费者依赖目标异常类型、错误码或边界协议执行稳定恢复、响应或错误映射；
- catch 恢复线程中断标记、回滚事务、释放资源、添加 suppressed、补偿状态或隔离单个批处理失败；
- SSE、JDK/框架回调或接口签名要求把受检异常适配为既有非受检协议；
- catch 按用户明确要求或既有框架契约更新最终状态，随后原样重抛，而且没有既有上层边界能等价完成该责任；
- 解析失败按当前契约回退默认值，或外部/业务异常在真正拥有协议的边界被转换；
- 只看到 catch-and-throw 形状，尚未核实调用方、协议、资源、中断和观测责任。

## 不合规与合规示例

不合规：私有写入方法捕获 `IOException`，只抛出 `new IllegalStateException("写入失败", e)`；调用方不按 `IllegalStateException` 恢复，统一边界也不依赖该消息。

不合规：框架适配器先原样重抛 `RuntimeException | Error`，再把其余 `Throwable` 包装成通用异常，但公开消费者没有该通用异常协议。

合规：框架适配器的底层契约明确为任意 `Throwable`，采用目标项目允许的方式直接传播；另一层窄 catch 按用户明确要求更新最终失败状态并原样重抛，因为 finally 需要该状态且上层无法等价补记。

合规：并行等待捕获 `InterruptedException` 后恢复线程中断标记并结束当前生命周期；这不是无价值包装。

## 最小修复

删除无处理价值的 try/catch，让原异常直接传播。受检异常只源于实现细节时，在最小非协议方法采用目标项目允许的收口方式；不要把 `@SneakyThrows` 的参数列表当成稳定外部异常契约。同步删除仅服务包装的 import、throws 和失真 Javadoc，同时保留真实业务或协议转换、清理、中断、观测与框架适配，不重构相邻异常体系。

## 报告要求

报告准确位置、原异常来源、包装后的类型或消息、真实调用方与异常消费者、catch 当前是否承担恢复、清理、协议或观测责任、删除后的行为差异和最小修复。若建议 `@SneakyThrows`，必须遵守目标项目已启用的 Java Rule，并说明没有稳定受检异常消费者的依据；证据不足时标为未验证，不按字符串数量报告。
