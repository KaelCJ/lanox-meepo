# Java 审计规则维护契约

> 只在用户明确授权新增、修改或废止 `nest-audit-java` 规则时读取。本文件与规则目录、模式方法和细则文件共同构成 Skill 内部闭环，不依赖目标项目 Java Rule 补足审计语义。

## 纳入条件

只有同时满足以下条件的问题才进入内部审计规则库：

1. 已有真实代码、调用关系、运行结果或可复核失败证明问题存在；
2. 问题能够跨单次文件或工作项复现为稳定判定，而不是个人风格或一次性事实；
3. 能写出至少一个不应命中的反例，避免把线索升级为机械门禁；
4. 能给出最小修复方向和修复后应保持的行为边界；
5. 已取得规则沉淀写入授权。

证据不足时保留在工作项或审计报告中，不创建“先占号”的空规则。

## 必备字段

每个 `NJA-<三位编号>` 或 `NJX-<三位编号>` 细则文件必须独立包含：

- 元数据：状态、类型、质量属性、默认级别、标签和适用范围；
- 为什么是问题：可观察风险与最坏合理后果；
- 触发调查：用于缩小搜索范围的代码或改动信号；
- 判定所需证据：命中前必须核实的调用、契约、行为或所有权事实；
- 不应报告：框架要求、真实硬边界、生成所有权等反例；
- 不合规与合规示例：说明语义差异，不绑定单一项目类名；
- 最小修复：消除根因且不扩大当前授权的改法；
- 报告要求：本规则特有的证据和未验证边界。

## 分类与级别

- 类型使用 `Bug`、`Vulnerability`、`Security Hotspot` 或 `Code Smell`；不能证明代码更可能错误时，不标为 Bug。
- 质量属性使用 `可靠性`、`安全性`、`可维护性`，可以多选。
- 默认级别使用 `阻断`、`重大`、`普通`、`建议`。默认值表达规则通常影响；本次实际级别必须根据真实影响调整并给出依据。
- 状态使用 `Ready`、`Beta`、`Deprecated`。废止规则保留 ID，不复用编号，并在目录中说明替代或停止原因。

## 文件与编号

- 通用规则使用 `NJA-*`，异常专项规则使用 `NJX-*`；规则族表达审计模式，不表达项目、模块或严重级别。
- 一条规则一个直属 `references/<规则族>-<编号>-<slug>.md` 文件，由 `rule-catalog.md` 直接链接；不建立更深的规则子目录。
- 新编号取所属规则族当前最大已占用编号加一；已使用编号不回收，不因重命名、迁移或并入统一入口而改变。
- `SKILL.md` 只保存共享流程、模式路由和只读边界；模式方法文件只保存该模式的候选扫描、证据模型和报告补充要求；具体判定只保存在独立细则文件，目录只保存导航摘要。
- 规则之间共享的维护方法写在本文件；不得把多个规则的成立条件或排除条件抽成必须深层追踪的第二规则库。

## 产出与审计规则沉淀

同一可复用 Java 问题获准规则化时，执行两次独立建模：

1. 在目标项目 Java Rule 的真实所有者中写产出前约束：适用条件、必须或禁止的选择、必要例外和冲突处理；
2. 在本 Skill 中写产后审计规则：触发线索、判定证据、误报排除、分类级别、示例、修复和报告要求；
3. 在对应工作项记录问题来源、两个规则位置、实际整改和验证事实。

两边允许共享同一事实来源，但正文必须各自完整；不得让一边只写“参见另一边”，也不得建立自动同步或共享正文文件。只读审计只能提出沉淀建议，不能执行上述写入。

## 写后检查

- 规则目录中的 ID、标题、类型、默认级别、触发条件和链接与细则一致。
- `SKILL.md` 能按模式定位规则目录和模式方法，规则目录能直接定位每个细则，没有孤儿规则或深层引用。
- 每条规则都同时包含命中证据和不命中反例，示例不会泄露凭据或绑定当前项目秘密。
- 项目 Java Rule 缺失或未启用时，本规则仍可独立理解和执行。
- 运行 Skill 目录校验，并用至少一个命中示例和一个反例进行只读前向验证；静态校验不能冒充真实宿主加载验收。
