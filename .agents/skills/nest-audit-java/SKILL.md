# Java 代码审计

## 输入与模式

- 已明确文件、模块、仓库、提交范围或“当前 Java 改动”时直接审计，不重复询问。
- 没有可定位目标时，只请求用户指定范围，不扫描、不写入。
- 普通 Java 审计使用通用模式，只选择 `NJA-*` 候选规则；不自动把全部 `catch` 扩张为异常专项扫描。
- 用户明确要求审计异常捕获、包装、吞没、重复异常日志、入口兜底或 AI 生成的异常处理时，使用异常专项模式，只选择 `NJX-*` 和适用的项目规则，不扩张为普通 Java 全面审计。
- 用户同时要求全面审计和异常专项审计时分别执行两种模式，分别给出范围、规则来源和结论，避免重复报告同一根因。

## 读取

1. 使用目标当前宿主生效的项目治理入口，并按其声明加载本次审计适用的工程规则；存在聚合目录或多仓时分别定位真实仓库。入口、规则所有者或正文缺失、为空、不可读、未完整加载或冲突时，停止受影响判断并报告准确缺口。
2. 当前上下文未完整保有本 Skill 最新的 [规则目录](references/rule-catalog.md) 时完整读取；否则复用。规则目录、规则格式或引用规则缺失、无效或不可读时停止审计并报告。
3. 使用异常专项模式时，每次作出结论前完整读取 [异常专项审计方法](references/exception-audit.md)；该文件只定义专项流程和证据模型，具体判定以 `NJX-*` 细则为准。
4. 冻结范围：“当前改动”覆盖工作区、暂存区和相关未跟踪 Java 文件；指定文件、diff 或提交时仍读取完整文件和当前调用关系。
5. 优先用 `rg` 查找生产调用方、实现、继承、注册和配置；按需读取相邻实现、构建文件、契约和运行证据，不凭类名、字符串命中或补丁片段推断职责。

## 规则选择与判定

1. 按当前模式、目标语言、框架、改动形态和调用关系，从规则目录选择候选规则；通用模式不选择 `NJX-*`，异常专项模式不选择 `NJA-*`。
2. 每个 Agent 在作出结论前，若当前有效上下文未完整保有候选细则的最新正文，则完整读取对应文件；不为没有触发条件的规则制造问题。委派审计时显式要求子 Agent 使用本 Skill 及准确模式，不复制目录或细则正文。
3. 通用规则以 `NJA-<三位编号>` 标识，异常专项规则以 `NJX-<三位编号>` 标识。每条规则必须独立包含分类、严重级别、触发条件、证据要求、排除条件、示例和最小修复方向。
4. 两个内部规则族共同构成本 Skill 的内部审计真源；项目启用的 Java Rule 只补充当前项目约束。缺少项目 Rule 不能把内部规则审计写成通过，项目 Rule 冲突也不能静默改写内部规则。
5. 项目产出规则以其自身 ID 标识并报告来源，不与 `NJA-*` 或 `NJX-*` 合并为一个规则 ID。
6. 审计过程中只读，不新增、修改、废止或自动同步规则。发现可复用的新问题时，在报告中分别提出产出规则与审计规则的沉淀建议；规则写入作为获得授权后的新工作项产物处理。

## 通用审计方法

1. 先建立功能基线：真实入口、生产调用方、外部契约、状态、输出、副作用、异常、性能要求和当前证据。无法确认行为等价时，不以代码更少为由认可改变。
2. 按真实影响检查控制流、空值、异常、资源、事务、一致性、并发、安全、序列化、框架回调和当前消费者兼容；不机械展开无关类别。
3. 将每个新增文件、类型、依赖、分支、配置和重构关联到用户目标、正式方案、项目规则或已验证问题；范围外重构、未来升级和无消费者兼容设计属于未授权扩张。
4. 涉及通用能力时先核对项目已有依赖和实际可用的 Nest 源码、API、语义、生命周期及依赖方向；有匹配能力时不重复实现，没有匹配时也不机械套用。
5. 对新增或扩大的接口、层级、Processor、Factory、Strategy、Helper 和扩展点寻找当前依据，并构造最小内联方案比较认知成本。只有真实复用、多个实现、独立复杂算法或外部 IO、事务、生命周期、并发、安全等硬边界能够支撑抽象。
6. 同时寻找机械极简的反例：现有稳定边界、框架要求、复杂状态或多个真实消费者可能证明独立类型合理。文件少、类少、方法短都不是目标。
7. 核对验证证据经过真实入口并符合项目测试口径；编译成功、局部绿色或 JavaDoc 不能证明行为和设计合理。
8. 主动搜索未读取的调用方、反射、SPI、注解注册、生成代码、失败输入和并发时序，同时尝试证明实现判断与审计判断都可能错误。

## 异常专项方法

- 按[异常专项审计方法](references/exception-audit.md)扫描候选、还原异常传播链、核对真实处理责任，并使用 `NJX-*` 细则判定。
- 同一根因沿多层重复包装、吞没或记录时合并为一个调用链问题，不按 `catch` 数量制造发现。
- 同一底层异常存在多个入口时，分别核对 HTTP、流式、HTML、RPC、任务和命令行等入口的真实行为，不要求入口使用相同异常类型、状态或用户提示。
- 批量或全仓专项审计必须基于最新工作树重新列出全部候选，并统计“有依据保留”“已证实问题”“未确认”三类数量。

## 问题与输出

- 问题分为阻断、重大、普通、建议；个人风格、类数量或行数本身不构成问题。
- 每个问题给出：规则 ID 与来源、级别和标题、准确位置、调用关系或当前事实、具体影响和最小修改建议；只有影响判定时才给出排除条件或适用反例，证据不足时标为未验证。
- 第一行直接给出总体判断；其后只输出已证实的问题、必要的证据边界和下一步。没有对应内容时不输出空栏目，不复述读取、搜索、抽象比较或检查过程。
- 异常专项问题还要给出原异常来源、`catch` 实际动作、传播后的异常事实、最终入口和用户可见结果；批量或全仓专项审计同时报告候选总数及三类数量。
- 同时执行两种模式时按模式分组；同一根因同时命中多个内部规则时合并影响并保留所有真实成立的规则 ID。
- 规则目录中的字段是报告最低信息，不要求每个问题都拥有自动化扫描器；证据不足时不能凭规则名称推断命中。

## 规则沉淀

- 只读审计不产生规则写入授权；获得新增、修改或废止授权后，先完整读取 [规则维护契约](references/rule-authoring.md)，再按其要求修改目录和细则。

## 只读边界

- 默认不修改代码、测试、文档、配置、Git 索引或工作项状态，也不执行会产生副作用的构建、测试或启动。
- 修复、生成持久审计报告、修改规则和规则库作为新的实现任务处理；只有未执行动作影响完成性、证据边界或后续决定时才报告。
